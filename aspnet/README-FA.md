# راهنمای استقرار — سامانه منابع انسانی (ASP.NET Core 8)

نسخه C# کامل سامانه (مهاجرت از Next.js — فاز 8 PLAN.md). این سند نحوه اجرا در سندباکس و پروداکشن ویندوز/SQL Server را توضیح می‌دهد.

---

## ۱. معماری

```
┌────────────────────────────┐        ┌──────────────────────────────┐
│  HrAttendance.Web          │        │  HrDeviceGateway (C# WinSvc) │
│  ASP.NET Core 8 MVC/Razor  │◄──────►│  ASP.NET Core 8 Worker       │
│  EF Core (SqlServer|Sqlite)│  HTTP  │  پروتکل ZK باینری + پل ADMS  │
│  احراز JWT + کوکی hr_at    │        │  sc.exe → Windows Service    │
└──────────┬─────────────────┘        └──────────┬───────────────────┘
           │                                     │ TCP 4370 / ADMS PUSH
           ▼                                     ▼
   ┌───────────────┐                    ┌──────────────────────┐
   │  SQL Server   │                    │  دستگاه‌های ZKTeco/…  │
   │  (پیش‌فرض)     │                    │  حضور و غیاب + تردد  │
   └───────────────┘                    └──────────────────────┘
```

- **وب**: `aspnet/src/HrAttendance.Web` — Razor سمت سرور، RTL فارسی، فونت وزیرمتن خوداتکا، تقویم جلالی با `PersianCalendar` داخلی .NET، نمودارها با Chart.js خوداتکا، خروجی اکسل با ClosedXML.
- **سرویس دستگاه‌ها**: `device-service-csharp/HrDeviceGateway` — بدون تغییر؛ قرارداد API وب حفظ شده است.
- **دیتابیس**: پیش‌فرض SQL Server؛ برای توسعه/سندباکس SQLite (سوییچ با config، بدون تغییر کد).

## ۳. پروداکشن ویندوز + SQL Server

1. **پیش‌نیاز**: .NET 8 SDK/Runtime + SQL Server 2019+
2. **کانفیگ** `appsettings.json` (یا متغیرهای محیطی):
   ```json
   { "Database": { "Provider": "SqlServer" },
     "ConnectionStrings": { "SqlServer": "Server=.;Database=HrAttendance;Trusted_Connection=True;TrustServerCertificate=True;MultipleActiveResultSets=true" } }
   ```
   متغیر محیطی معادل: `Database__Provider=SqlServer`
3. **ساخت اسکیما**: در اولین اجرا خودکار (`EnsureCreated`). اگر پایگاه داده را دستی ساخته‌اید و خالی است، برنامه اسکیمای کامل را روی همان می‌سازد؛ اگر اسکیمای ناسازگار داشته باشد، پیغام شفاف با راهنمای حذف (`DROP DATABASE`) نمایش داده می‌شود. برای تولید `SeedDemo=false` و ایجاد دستی ادمین از طریق اولین ورود (seedRBAC همیشه اجرا می‌شود).
4. **انتشار**:
   ```bat
   cd aspnet\src\HrAttendance.Web
   dotnet publish -c Release -r win-x64 --self-contained -o publish\web
   sc create HrAttendanceWeb binPath= "publish\web\HrAttendance.Web.exe" start= auto
   ```
   (یا اجرای مستقیم `dotnet run` پشت IIS/Kestrel با reverse-proxy)
5. **سرویس دستگاه‌ها**: مطابق `device-service-csharp/README-FA.md` — `publish.bat` سپس `install-service.bat`.
6. **امنیت**: مقدار `Jwt:Secret` را حتماً با یک کلید ۲۵۶بیتی تصادفی جایگزین کنید؛ HTTPS را روی reverse-proxy فعال کنید؛ رمز حساب‌های پیش‌فرض را از صفحه «کاربران» بازنشانی کنید.

## ۴. تست صحت (E2E)

```bash
bash scripts/e2e-aspnet.sh        # قرارداد API + صفحات + RBAC + اکسل
bash scripts/e2e-gateway.sh       # چرخه کامل: صف وب → گیت‌وی TCP → دستگاه شبیه‌سازی → ACK
bash scripts/e2e-biometrics.sh    # داده‌های هویتی: دریافت پرسنل/قالب از دستگاه + انتقال بین دستگاه‌ها
```

نتیجه مورد انتظار: صف دستور unlock از پنل → اجرا روی دستگاه TCP → وضعیت `acked` («درب به مدت 5 ثانیه باز شد») → وضعیت دستگاه آنلاین با Firmware و شمار کاربران.

## ۴‑ب. داده‌های هویتی دستگاه‌ها (بایومتریک)

چرخه کامل هویت پرسنل با دستگاه‌ها — پنل `/Biometrics` (مجوز `biometrics.view` / `biometrics.manage`):

1. **دریافت پرسنل از دستگاه** (`get_users`): فهرست کاربران حافظه دستگاه خوانده می‌شود؛ کاربران با کد پرسنلی به رکورد پرسنل پیوند می‌خورند و پرسنلی که در سامانه نیست به‌طور خودکار در دیتابیس ساخته می‌شود (نوع همکاری «قراردادی»، شناسه ملی موقت `DEV-{سریال}-{پین}` — باید توسط کارگزینی تکمیل شود).
2. **دریافت اطلاعات هویتی** (`get_user_bios`): قالب اثر انگشت (اسلات ۰ و ۱)، چهره، شماره کارت و رمز از دستگاه خوانده و در جداول `DeviceBiometric` (کپی per-device) و `EmployeeBiometric` (کپی مرجع) ذخیره می‌شود.
3. **انتقال به دستگاه‌های دیگر** (`push_user_bios`): انتخاب چند پرسنل × چند دستگاه مقصد — کاربر + کارت/رمز + قالب‌های اثر انگشت/چهره روی دستگاه مقصد نوشته می‌شود (CMD_USERTEMP_WRQ). دیتابیس نقش هاب انتقال را دارد؛ هر قالب «منبع» آخرین دستگاه دریافت را نگه می‌دارد.
4. **حذف کاربر از دستگاه** (`delete_user`) + پاک‌سازی نسخه محلی.
5. **شبیه‌ساز نمایشی**: برای محیط بدون سخت‌افزار، پاسخ دستگاه از همان مسیر پردازش رسمی اعمال می‌شود.

قرارداد گیت‌وی (رویدادهای جدید/تغییریافته): رویداد `users` با فیلدهای کامل `uid/privilege/card/password/group`، رویداد جدید `bios` با `pin/type/index/valid/quality/data(base64)`؛ دستورهای `get_user_bios` و `push_user_bios`. پروتکل قالب‌ها: CMD_USERTEMP_RRQ(9)/WRQ(10) با `typeFlag` (0=اثر انگشت، 1=چهره).

## ۶. ماژول کنترل پارکینگ (فاز ۴۰)

ماژول «کنترل پارکینگ» در منوی سایدبار (گروه «پارکینگ») با ۵ تب: تابلوی پارکینگ، پارکینگ‌ها و گیت‌ها، خودروها، مجوزها و رویدادها.

- **موجودیت‌ها**: `ParkingLot` (پارکینگ با ظرفیت و حق پارکینگ ماهانه) → `ParkingGate` (گیت/راهبند متصل به دستگاه) ، `Vehicle` (خودروی پرسنل، پلاک‌محور)، `ParkingPermit` (مجوز دائم/موقت با جایگاه اختصاصی)، `ParkingEvent` (ورود/خروج با نتیجه ارزیابی).
- **موتور ارزیابی عبور** (شبیه‌ساز پلاک‌خوان در تب رویدادها/دکمه «ثبت عبور خودرو»): به‌ترتیب گیت فعال/حالت راهبند (نرمال/باز دائم/قفل دائم) → هم‌خوانی جهت گیت → وجود پلاک در خودروها → فعال‌بودن خودرو → مجوز معتبر همان پارکینگ → آنتی‌پس‌بک (عبور تکراری) → ظرفیت پارکینگ. عبور غیرمجاز = رویداد + هشدار امنیتی (منبع «کنترل پارکینگ»).
- **پلاک‌محور**: پلاک به‌صورت نرمال‌شده (بدون فاصله و «ایران») به‌ازای هر شرکت یکتا است؛ سابقه رویدادها حتی پس از حذف خودرو با متن پلاک حفظ می‌شود.
- **دسترسی‌ها**: `parking.view` / `parking.manage` / `parking.control` (در نقش‌های اپراتور تردد، حراست، مشاهده‌گر و سرویس پل تخصیص یافته است).
- **اسکیما**: جدول‌های پارکینگ با مکانیزم خودترمیم (CreateMissingTables) در اولین اجرا روی هر دو پروایدر SQLite/SQL Server خودکار ساخته می‌شوند — برای دیتابیس‌های موجود هیچ اقدامی لازم نیست.

## ۷. دوربین‌های پلاک‌خوان و ثبت خودکار تردد خودرو (فاز ۴۱)

دوربین‌های ANPR همان الگوی دستگاه‌های تردد — SN و توکن webhook، صف دستور، ضربان و وضعیت آنلاین/آفلاین. تب «دوربین‌های پلاک‌خوان» در صفحه کنترل پارکینگ.

- **موجودیت‌ها**: `AnprCamera` (متصل به یک `ParkingGate`، برند/مدل/IP/جهت لاین/آستانه اطمینان/آدرس RTSP، SN و توکن یکتا) و `AnprCommand` (صف دستور: `open_barrier`/`close_barrier`/`ping`/`restart` با چرخه pending→delivered→acked).
- **ثبت خودکار**: دوربین پلاک خوانده‌شده را به `POST /api/anpr/webhook` (رویداد `plate`، تک‌پلاک یا آرایه `reads`) با هدر `X-Device-Token` می‌فرستد؛ سامانه پلاک را نرمال می‌کند، آستانه اطمینان دوربین را چک می‌کند و همان موتور ارزیابی فاز ۴۰ را اجرا می‌کند — رویداد ورود/خروج با متد «پلاک‌خوان»، `CameraId` و درصد اطمینان ثبت و در صورت مجاز بودن `barrier: open` برگردانده می‌شود.
- **قرارداد پل** (کامل مثل دستگاه‌ها): `GET api/anpr/webhook?SN=` → ضربان + تحویل دستورات صف‌شده؛ `POST` با `event: ping|status|plate|ack`؛ `GET api/anpr` فهرست دوربین‌ها (Bearer سرویس پل با دسترسی `devices.poll`).
- **کنش‌های UI**: ضربان (صف ping)، آنلاین‌سازی دمو (ضربان شبیه‌سازی‌شده)، بازکردن راهبند از راه دور (صف open_barrier)، فعال/غیرفعال، چرخش توکن. قطع دوربین → هشدار «قطع دوربین» (بدون تکرار) و اتصال مجدد → رفع خودکار آن.
- **شبیه‌ساز**: در تب رویدادها با انتخاب دوربین، ثبت عبور از همان مسیر خودکار دوربین می‌گذرد (CameraId + اطمینان تولیدشده).
- **اسکیما**: جدول‌های `AnprCameras`/`AnprCommands` خودترمیم؛ ستون‌های `ParkingEvents.CameraId/PlateKey/Confidence` نیز روی دیتابیس‌های موجود خودکار اضافه می‌شوند (PatchSchema فاز ۴۱) — مهاجرت دستی لازم نیست.

## ۸. نمای زنده و گزارش ورود/خروج خودروها (فاز ۴۲)

### نمای زنده (تب «📹 نمای زنده» در کنترل پارکینگ)

دیوار دوربین‌های پلاک‌خوان به‌سبک مانیتورینگ CCTV: هر دوربین یک کاشی تصویر زنده با خط اسکن، نشانگر REC، وضعیت آنلاین/آفلاین («بدون سیگنال»)، آخرین پلاک خوانده‌شده به‌شکل چیپ پلاک ایرانی روی تصویر (با درصد اطمینان، جهت و صاحب خودرو) و کنش‌های سریع (اتصال/ضربان/بازکردن راهبند). ستون کنار: تیکر «خوانش‌های زنده» (فلش ردیف رویداد تازه) و فهرست «داخل پارکینگ» (پلاک + صاحب + پارکینگ + زمان ورود). داده‌ها هر ۶ ثانیه از `GET /Parking/LiveData` (JSON، دسترسی `parking.view`) به‌روزرسانی می‌شود.

### گزارش ورود/خروج خودروها (PDF/Excel)

- **صفحه گزارش**: «گزارش‌ها ← 🚗 گزارش ورود/خروج خودروها» یا دکمه‌های «گزارش کامل/اکسل/PDF» در تب رویدادهای پارکینگ.
- **فیلترها**: بازه تاریخ (پیش‌فرض ماه جاری)، شرکت، پارکینگ، جهت (ورود/خروج)، نتیجه (مجاز/غیرمجاز)، روش ثبت (پلاک‌خوان = ثبت خودکار دوربین ANPR / کارت / دستی).
- **خروجی اکسل**: `/Reports/ParkingXlsx` — ۱۵ ستون (زمان میلادی + تاریخ جلالی + ساعت، پلاک، صاحب خودرو، نوع، شرکت، پارکینگ، گیت، جهت، روش، دوربین، اطمینان، نتیجه، دلیل رد) با RTL و سرستون یخ‌زده؛ حداکثر ۱۰۰ هزار ردیف.
- **خروجی PDF**: `/Reports/ParkingPdf` — A4 افقی با KPI کلی (کل/ورود/خروج/مجاز/غیرمجاز/خوانش خودکار) + ریز رویدادها؛ هم‌تم پالت فعال ادمین.
- **دسترسی‌ها**: صفحه با `reports.view`، خروجی‌ها با `reports.export` (حسابرسی export ثبت می‌شود).

## ۹. نمای زنده حراست + پالت «پارسان» (فاز ۴۳)

### نمای زنده حراست (منوی «کنترل تردد ← 📡 نمای زنده حراست»)

پنل رصد لحظه‌ای ترددهای دستگاه‌های آماربَر، ویژه اتاق حراست:

- **دیوار دستگاه‌ها**: هر دستگاه یک قاب تصویری زنده (خط اسکن، OSD با برند/IP، نشانگر آنلاین/آفلاین «بدون اتصال»)، آواتار بزرگ آخرین فرد اسکن‌شده، نام و جهت و کد پرسنلی آخرین تردد، شمارش تردد امروز و زمان آخرین اتصال.
- **تیکر «ترددهای زنده»**: ۸۰ اسکن آخر با نام، کد پرسنلی، واحد سازمانی، دستگاه و زمان؛ ردیف‌های تازه فلش می‌خورند. نشان‌های جهت: «⬅ ورود» (نخستین اسکن روز)، «خروج ➡» (آخرین اسکن روز)، «⬌ تردد» (اسکن میانی) و «⚠ ناشناس» (کد پرسنلی ناشناخته).
- **نوتیفیکیشن زنده**: هر تردد جدید بلافاصله یک کارت اعلان با اطلاعات کامل فرد (نام، کد پرسنلی، واحد، شرکت، دستگاه، جهت، زمان) در گوشه صفحه می‌آید و تا ۹ ثانیه می‌ماند (حداکثر ۵ کارت هم‌زمان؛ کلیک = بستن).
- **چیپ‌های وضعیت**: دستگاه‌ها/آنلاین، تردد امروز، اسکن ناشناس امروز، زمان آخرین تردد.
- **منبع داده**: هر اسکن دستگاه (وب‌هوک زنده یا دریافت دسته‌ای حافظه آفلاین) در جدول جدید `DevicePunchLogs` یک ردیف خام با جهت استنباط‌شده ثبت می‌کند و صفحه هر ۶ ثانیه از `GET /Devices/PunchFeed` (JSON، دسترسی `devices.view`) تغذیه می‌شود. فیلتر شرکت هم پشتیبانی می‌شود.
- **ارتقای خودکار**: جدول `DevicePunchLogs` در اولین اجرا روی دیتابیس‌های موجود (SQLite و SQL Server) خودکار ساخته می‌شود و از رکوردهای ۳ روز اخیر backfill می‌گیرد — هیچ اقدامی لازم نیست.

### پالت «پارسان» (قالب داشبورد مدرن)

پالت ششم کتابخانه پالت‌های استاندارد (تنظیمات ← کتابخانه پالت) — برداشت مستقیم از داشبورد مرجع: منوی سرمه‌ای تیره `#17293a`، اکسنت فیروزه‌ای `#14b8a6`، زمینه روشن آبی‌خاکستری و وضعیت‌های پرانرژی. این پالت به‌صورت خودکار **پالت فعال** می‌شود (فقط اگر ادمین پالت دیگری انتخاب نکرده باشد) و کل نرم‌افزار، نمودارهای داشبورد و خروجی‌های PDF را هم‌رنگ می‌کند.

### قالب داشبورد «پارسان»

داشبورد اصلی با همان زبان بصری تصویر مرجع بازطراحی شد: ردیف کارت‌های آمار پاستلی با آیکون‌چیپ رنگی (حاضران/تأخیر/غایب/دستگاه آنلاین/تردد گیت‌ها/درخواست‌ها/هشدار/مهمان)، نمودار میله‌ای انباشته حضور ۷ روزه + نمودار حلقه‌ای مناطق با پالت رنگی پارسان، و نوار «دستگاه‌های متصل» با برند، IP، محل نصب، وضعیت اتصال، شمارش تردد امروز و آخرین فرد اسکن‌شده. هیچ KPI یا میانبری از نسخه قبل حذف نشده است.

## ۱۰. سازندهٔ بصری فرمول (Drag & Drop) — فاز ۴۴

نوشتن فرمول اقلام حقوق دیگر نیازی به تایپ ندارد. در پاپ‌آپ «قلم جدید/ویرایش قلم» و پنل «آزمایش فرمول»، یک **سازندهٔ بصری** بالای کادر فرمول می‌نشیند:

- **پالت ۵ تبیده**: «متغیرها» (۳۷ متغیر زمینه با جستجو و راهنمای هرکدام)، «توابع» (round/if/قلم/مالیات و… با امضای کامل)، «اقلام» (کدهای اقلام واقعی همین شرکت — کلیک = `قلم('کد')`)، «عملگرها» (`+ − * / % ^ ( ) < <= > >= == != && || !`) و «عدد/متن» (افزودن عدد یا رشتهٔ دلخواه).
- **Drag & Drop واقعی**: بلوک را از پالت به بوم بکشید؛ داخل آرگومان توابع هم می‌توان رها کرد (توابع بلوک تو در تو می‌سازند با اسلات جدا برای هر آرگومان). جابجایی ترتیب با درگ، حذف با رهاکردن روی پالت یا دکمه ✕. **کلیک ساده روی بلوک پالت = افزودن به انتها** (برای کسانی که درگ راحت نیست).
- **همگام‌سازی زنده**: هر تغییر بلافاصله به کادر فرمول (textarea اصلی) نوشته می‌شود و پیش‌نمایش متن زیر بوم به‌روز می‌شود. دکمه «✍️ نوشتن دستی» همیشه هست — فرمول‌های دستیِ قابل‌تجزیه به‌صورت بلوک باز می‌شوند و فرمول خراب با پیام فارسی در حالت نوشتن می‌ماند.
- **ویرایش درجا**: کلیک روی بلوک عدد/متن → کادر کوچک → Enter تأیید، Esc لغو. ارقام فارسی و ممیز «٫» خودکار نرمال می‌شوند.
- **هوشمندی**: پارسرِ سمت مرورگر همان گرامر و تقدم موتور سرور (`PayrollFormula`) را دارد؛ پرانتزهای لازم در بازسازی حفظ می‌شوند (`(a+b)*c` همان می‌ماند)، آرگومان خالی تابع با رنگ هشدار مشخص و موقتاً «۰» نوشته می‌شود و اگر فرمول قابل تبدیل نباشد سازنده بی‌صدا از راه می‌رود — رفتار قبلی هرگز نمی‌شکند (اگر JS لود نشود فرم دستی مثل قبل است).
- **ذخیره**: همان `POST /Payroll/ItemSave` قبلی با اعتبارسنجی `SyntaxCheck` سمت سرور؛ فرمول ساخته‌شده با بلوک‌ها دقیقاً همان متنی است که موتور محاسبه اجرا می‌کند.

همراه این فاز، یک باگ نهفته فرم‌ها هم رفع شد: فرم «ایجاد» قلم/پارامتر به‌دلیل Id خودکارِ entityها، `id` تصادفی می‌فرستاد و سرور مسیر «ویرایش» را می‌رفت (پاسخ 404) — حالا در Create فیلد id خالی ارسال می‌شود.

## ۱۱. سرویس گیت‌وی C# — پشتیبانی دوربین‌های پلاک‌خوان (فاز ۴۴)

سرویس ویندوزی `HrDeviceGateway` (نسخه ۲.۱) حالا علاوه بر دستگاه‌های تردد ZK، **دوربین‌های پلاک‌خوان** را هم پوشش می‌دهد:

- **دریافت خودکار فهرست دوربین‌ها**: پاسخ `api/gateway/config` فیلد جدید `cameras` دارد (سریال/نام/IP/برند/گیت/فاصله ضربان). گیت‌وی برای هر دوربین فعال یک حلقه مستقل می‌سازد.
- **ضربان و وضعیت آنلاین**: هر حلقه هر `HeartbeatSec` ثانیه `GET api/anpr/webhook?SN=…` می‌زند → `MarkSeen` سرور → دوربین در پنل «آنلاین» دیده می‌شود حتی اگر خود دوربین به گیت‌وی دسترسی مستقیم نداشته باشد.
- **پل پلاک (`AnprBridge`)**: دوربین‌هایی که POST سفارشی دارند خوانش را به گیت‌وی می‌زنند و گیت‌وی با قرارداد سرور به موتور مجوز پارکینگ می‌رساند:
  - `POST /anpr/plate?SN=…` یا `POST /anpr/{sn}/plate` — بدنه JSON (`{"plate":…}` یا دسته‌ای `{"reads":[…]}`)، form-urlencoded، متن خام یا حتی `?plate=…` در کوئری. نام فیلدهای رایج سازنده‌ها (plate/plateNo/plateNumber/…، confidence/score/similarity) شناخته می‌شود.
  - جهت خروجی/ورودی به «ورود»/«خروج» نرمال می‌شود و **پاسخ کامل موتور** (مجاز/غیرمجاز، باز/بسته بودن راهبند، مالک خودرو، شمارش پلاک ناشناس) عیناً به فرستنده برمی‌گردد — دوربین/دستگاه کنترل راهبند می‌تواند بر اساس `barrier=open` خودش تریگر شود.
  - `GET /anpr/ping?SN=…` — ضربان + شمارش دستورات در انتظار (فقط نگاه؛ مصرف با حلقه اجرا).
- **اجرای دستورات راهبند**: دستورهای صف‌شده پنل (`open_barrier`/`close_barrier`/`restart`/`ping`) در ضربان تحویل گرفته می‌شوند؛ `ping` مستقیم ack می‌شود و راهبند/ری‌استارت به **قالب HTTP خود دوربین** رله می‌شود که در `appsettings.json → Gateway:Anpr:Cameras` با `{ip}` پیکربندی می‌شود (Hikvision ISAPI، Dahua CGI و…) با اعتبار Basic اختیاری. اگر قالب تنظیم نشده باشد دستور با پیام راهنمای فارسی `failed` می‌شود — نه بی‌صدا.
- **تنظیمات bootstrap**: بخش `Anpr` در `appsettings.json` با دوربین‌های نمونه؛ فهرست فعال همیشه از پنل ادمین می‌آید و قالب‌های HTTP از این فایل حفظ می‌شوند.

## ۱۲. ویزارد راه‌اندازی اولیه + پیکربندی بانک از فرم (فاز ۴۵)

نصب تازه دیگر نیازی به دستکاری `appsettings.json` ندارد:

- **نخستین اجرا**: گیت میانه همه مسیرها را به `/Setup` می‌فرستد. فرم ویزارد پروایدر (SQL Server با سرور/پورت/بانک/نوع احراز/SSL یا SQLite با مسیر فایل)، «تست اتصال» و «ذخیره و راه‌اندازی» دارد؛ بانک در صورت نبود خودکار ساخته می‌شود.
- **بدون ری‌استارت**: پس از ذخیره، `hrsettings.json` نوشته می‌شود، پیکربندی همان لحظه Reload می‌شود، اسکیما + سیدرها اجرا و کاربر به صفحه ورود هدایت می‌شود. سرویس‌های پس‌زمینه هم از اسکوپ بعدی با اتصال تازه کار می‌کنند.
- **پس از نصب**: «تنظیمات سامانه ← پایگاه داده» همین فرم را دارد — تغییر اتصال با تست، ساخت/خودترمیم بانک جدید و اعمال فوری؛ داده‌های بانک قبلی دست‌نخورده می‌ماند.
- **سازگاری قدیم**: نصب‌های موجود که `Setup:Configured` ندارند مستقیم بالا می‌آیند (فقط نصب تازه با `Configured=false` ویزارد می‌بیند). سندباکس با متغیر `Setup__Configured=true` از ویزارد عبور می‌کند.

## ۱۳. نوار بالایی مرجع + عکس پروفایل + پلاک واقعی (فاز ۴۵)

- **نوار بالایی** مطابق قالب مرجع بازطراحی شد: چیپ کاربر (عکس/آواتار + نام + سمت)، زنگ اعلان با نشان تعداد هشدارهای باز و دراپ‌داون ۶ مورد آخر، چرخ‌دنده تنظیمات، تاریخ جلالی + ساعت زنده، و **جستجوی سراسری** (`/Home/Search` — پرسنل/دستگاه‌ها/خودروها/کاربران با گارد دسترسی هر ماژول).
- **عکس پروفایل**: فرم ایجاد کاربر/پرسنل فیلد عکس دارد؛ فهرست‌ها آواتار کوچک می‌دهند؛ مودال «🖼 عکس» در کاربران؛ عکس در نوار بالایی، سایدبار و نمای زنده حراست (نوتیف و دیوار دستگاه‌ها) نمایش داده می‌شود. PNG/JPG/WEBP ≤ ۲MB در `wwwroot/uploads/avatars` با حذف خودکار فایل قبلی.
- **رفع باگ نمایش پلاک**: متن دوجهته (ارقام + «ایران») در RTL به‌هم می‌ریخت. کامپوننت `PlateFmt` (سرور) و `plateHtml()` (کلاینت) پلاک را به اجزا می‌شکنند و مثل **پلاک فلزی واقعی** می‌سازند: سریال «۲رقم حرف ۳رقم» چپ، کادر «ایران + کد استان» راست — در نمای زنده، تیکر، جدول خودروها/مجوزها/رویدادها. پلاک‌های غیراستاندارد هم به توکن‌های ایزوله در ترتیب منطقی رندر می‌شوند؛ الگوریتم bidi دیگر نمی‌تواند ترتیب را عوض کند.
- **بازآرایی منو**: دستگاه‌های تردد + نمای زنده + مناطق/گیت‌ها + کارت‌ها + ارباب‌رجوع + داده‌های هویتی زیر «کنترل تردد و حراست»؛ شیفت‌ها و تعطیلات به «منابع انسانی»؛ گیت‌وی و اعلان‌ها به «مدیریت سیستم».

## ۱۴. استودیو مجوز نصب — برنامهٔ مجزای تولید مجوز هر سرور (فاز ۴۷)

برنامهٔ مجزای ویندوزی (WinForms فارسی/راست‌به‌چپ) برای صدور مجوز نصب متصل به سخت‌افزارِ هر سرور:

- **سورس**: `tools/LicenseStudio` — **بستهٔ آماده (خودکفا، بدون نیاز به نصب .NET)**: `download/LicenseStudio.zip` (اکزی + `private.pem` + راهنما). ابزار عمومی است و از نسخهٔ ۱.۵.۲ بدون پیشوند HR عرضه می‌شود (پوشهٔ دادهٔ نصب قدیمی هم خودکار مهاجرت می‌شود).
- **تب‌ها**: «صدور مجوز» (اثر انگشت سرور + دارنده + تاریخ شمسی یا دائمی + سقف پرسنل + یادداشت)، «بررسی مجوز» (بازبینی هر فایل مجوز + تطبیق اثر انگشت)، «تاریخچهٔ صدور» (تمام مجوزهای صادرشده برای همهٔ سرورها — دوبار کلیک = کپی متن برای ارسال به مشتری)، «راهنمای کامل».
- **امنیت**: کلید خصوصی داخل سورس/باینری جاسازی نمی‌شود؛ برنامه `private.pem` کنار خودش را پیدا و مسیرش را به‌خاطر می‌سپارد. کلید عمومی در `LicenseService.PublicKeySpki` جاسازی است (فاز ۴۶ — کلید جدید فاز ۴۷).
- **راستی‌آزمایی**: موتور مشترک (`LicenseCore.cs`) در `scripts/LicenseCoreTest` با ۱۸ چک (امضا/دستکاری/ماشین اشتباه/انقضا/نرمال‌سازی/تاریخ شمسی) سبز؛ چرخهٔ کامل «صدور → آپلود در `/License` سرور واقعی → فعال‌سازی» هم تست شده است.
- **قفل‌گذاری روی سرور مشتری**: `"License": { "Mode": "Strict" }` در `appsettings.json` یا `hrsettings.json` — جزئیات کامل در `README-Licensing-FA.md`.

**تب «نمونه‌ها» در فرمول‌ساز بصری (همین فاز)**: پالت سازندهٔ Drag & Drop اقلام حقوق حالا ۱۲ قالب آمادهٔ فرمول‌های رایج دارد (اضافه‌کاری ۱٫۴، حق شب‌کاری، کسر غیبت/تأخیر/مرخصی بدون حقوق، بیمه ۷٪، مالیات پلکانی، حق اولاد، عیدی کارکرد، مأموریت، خالص پرداختی) — کلیک یا کشیدن کارت روی بوم، بلوک‌ها را می‌سازد و بعد می‌توانید نرخ‌ها را با کلیک روی بلوک عدد ویرایش کنید.

## ۱۵. معماری ماژولار سامانه — فازهای ۵۴ و ۵۵

سامانه به ۸ ماژول منطقی تقسیم شده است (انتخاب کاربر: گزینهٔ A — ماژولار در تک‌اپ): **۳ ماژول پایهٔ خاموش‌نشدنی** (core هستهٔ پلتفرم / org سازمان و پرسنل / devices تجهیزات و گیت‌وی) + **۵ ماژول سیستمی قابل خاموش/روشن** (attendance حضور / access کنترل تردد / visitors بازدیدکننده / payroll حقوق / parking پارکینگ). خاموش‌کردن هر ماژول فقط منو و مسیرهای آن را می‌بندد و داده‌ها دست‌نخورده می‌مانند؛ با روشن‌کردن مجدد همه‌چیز برمی‌گردد.

- **رجیستری**: `Modules/ModuleCatalog.cs` — هویت ماژول‌ها، آیتم‌های منو (BuildNav)، مانیفست کنترلرها و نگاشت کنترلر/اکشن ← ماژول. کنترلر ناشناخته = شکست باز (هرگز مسدود نمی‌شود).
- **وضعیت**: `Modules/ModuleStateService.cs` — فایل‌پشتیبان `App_Data/modules.json` (الگوی hrsettings؛ صفر تغییر مدل) + سقف مجوز از `LicensePayload.Modules` (فهرست‌دار فقط اگر مجوز «معتبر» باشد؛ null/خالی = بدون سقف).
- **گیت مسیر**: `Infrastructure/ModuleGate.cs` — صفحه → ریدایرکت `/Home/ModuleDisabled`، AJAX → 403 JSON، api/webhook → 503 JSON.
- **مدیریت**: کارت «ماژول‌های سامانه» در `/Settings` (toggle با حسابرسی `module_enable`/`module_disable`) + سطر «ماژول‌های مجاز» در `/License`.
- **فاز ۵۵ — بسته‌بندی Core**: کد ماژول core به `Modules/Core/Controllers` (۱۱ کنترلر: Home/Auth/Account/Users/Companies/Setup/Settings/Audit/Notifications/License/MvcBase) و `Modules/Core/Services` (AuthCore/SettingsService/Notifications/LicenseService/Security) منتقل شد — **فضانام‌ها عمداً بدون تغییر** تا جابه‌جایی صرفاً فیزیکی و بدون ریسک باشد. مانیفست `Controllers` هر ماژول در رجیستری، منبع یکتای نگاشت مسیرهاست (تعریف تکراری = خطای استارتاپ). Viewهای Razor به مسیر `Views/{Controller}` چسبیده‌اند و جابه‌جا نمی‌شوند.
- **گام‌های بعدی (فازهای ۵۶ به بعد)**: بسته‌بندی org و devices و سپس ماژول‌های سیستمی یکی‌یکی با همین الگو؛ وابستگی فقط یک‌طرفه (سیستم ← پایه) و بدون ارجاع مستقیم بین سیستم‌ها.

## ۱۶. تفکیک فیزیکی — هر ماژول یک پروژهٔ جدا + بستهٔ مشتری دلخواه (فاز ۵۷)

با درخواست کاربر («انتظار دارم هر ماژول در یک پروژهٔ جدا باشد؛ چون ممکن است بعضی ماژول‌ها را به مشتری تحویل ندهم»)، ساختار از «ماژولار منطقی در تک‌اپ» به **معماری چندپروژه‌ای با حذف ماژول در زمان بیلد** ارتقا یافت:

- **HrPlatform.Core** (`src/HrPlatform.Core`) — پلتفرم مشترک: موجودیت‌ها (Domain/Entities)، DbContext، هستهٔ احراز (AuthCore/Security)، فیلتر `[HasPerm]`، تقویم جلالی، پارسر پلاک، تنظیمات ظاهر، گزارش‌ساز (ReportService)، تولید PDF (PdfReport)، BuildInfo و کنترلر پایهٔ MvcBase. **فضانام‌ها عمداً همان قبلی‌اند** — جابه‌جایی صرفاً فیزیکی است تا مهاجرت‌ها/رفتار صفر ریسک بمانند.
- **HrModules.Parking** (`src/modules/HrModules.Parking`) — اولین ماژول سیستمی با پروژهٔ جدا (Razor Class Library): ParkingController + پل دوربین‌های ANPR (api/anpr) + ParkingOps + هر ۷ ویو. کنترل‌ها/ویوها در همین DLL کامپایل می‌شوند و به‌طور خودکار به اپ تزریق می‌شوند (Application Part).
- **سه لایهٔ در دسترس‌بودن ماژول**: ① نصب‌نشده (DLL در بسته نیست — بیلد مشتری) ② قفل با مجوز (فاز ۵۴) ③ خاموش/روشن با toggle مدیر. گیت مسیر برای «نصب‌نشده» پیام دقیق می‌دهد: صفحه → «در این نسخه نصب نشده است»، حتی وقتی کنترلر وجود ندارد (تشخیص از مانیفست رجیستری) و وب‌هوک غایب همان ۴۰۴ واقعی می‌ماند.
- **بستهٔ مشتری**: `scripts/build-customer.sh [mod1,mod2] [AppVersion] [Vendor]` — فقط هاست را publish می‌کند؛ DLL ماژول‌های حذف‌شده در خروجی وجود ندارد. پرچم هر ماژول: `-p:HrModuleParking=false` (فازهای بعد: HrModulePayroll/...).
- **بیلد کامل**: `dotnet build Platform.sln` — همهٔ ۳ پروژه؛ `HrBuildModules` (کد) تنها مرجع «حضور ماژول» است و از ثابت‌های کامپایل تعریف‌شده در csproj هاست تغذیه می‌کند.
- **قاعدهٔ فازهای بعدی**: هر ماژول سیستم = یک `HrModules.*` (RCL) متعهد فقط به HrPlatform.Core؛ نقاط مشترک (پرسنل/دستگاه/کارت/گزارش/پرتال من) در پلتفرم/هاست می‌مانند؛ اکشن‌های چند-ماژولی (Reports/Parking و ...) فعلاً در هاست‌اند و با ActMap گیت می‌شوند.

## ۱۷. تفکیک کامل — هر پنج ماژول سیستم پروژهٔ جدا + بستهٔ حداقلی (فاز ۵۸)

ادامهٔ فاز ۵۷ به درخواست کاربر («همهٔ ماژول‌ها را جدا کن؛ اگر DLLهای یک ماژول نبود، سیستم به مشکل نخورد و بقیه راحت کار کنند») — حالا **هر ۵ ماژول سیستمی** یک پروژهٔ مستقل Razor Class Library است و بستهٔ مشتری می‌تواند **هیچ DLL ماژولی نداشته باشد** و سامانه سالم بالا بیاید:

- **پروژه‌های ماژول** (`src/modules/`): `HrModules.Attendance` (تردد روزانه/شیفت‌ها/درخواست‌ها)، `HrModules.Access` (مناطق و گیت‌ها/کارت‌ها + موتور AccessControl)، `HrModules.Visitors` (ارباب رجوع)، `HrModules.Payroll` (لیست حقوق/فرمول‌ساز/فیش) + `HrModules.Parking` (فاز ۵۷). هر کدام: کنترلرها + همهٔ ویوها در همان DLL (AddRazorSupportForMvc) و تعهد فقط به HrPlatform.Core.
- **انتقال به پلتفرم مشترک** (فضانام بدون تغییر): `AttEngine`، `PayrollEngine`، `PayrollFormula` (چون DbSeeder هاست و موتورهای همدیگر و گزارش‌ها استفاده می‌کنند)، `EssAuth` (پرتال «من» هاست + کنترلر حقوق)، `DeviceOps` (کنترلر Access + هاست)، `Notifications` (NotificationEngine/Worker — کنترلر Access + هاست). قاعده: هر سرویسی که هم هاست و هم ماژول می‌خواهد → HrPlatform.Core؛ سرویس اختصاصی → همان ماژول.
- **پرچم‌های بیلد**: `-p:HrModuleAttendance=false -p:HrModuleAccess=false -p:HrModuleVisitors=false -p:HrModulePayroll=false` (+ پرچم Parking فاز ۵۷). HrBuildModules اکنون ۵ ثابت دارد؛ بیلد کامل sln و بیلد «فقط پایه‌ها» هر دو صفر خطا.
- **بوت‌تست واقعی بسته‌ها**: بستهٔ کامل (هر ۵ DLL) و بستهٔ حداقلی (بدون هیچ DLL ماژول) هر دو در Release publish و با بانک نو بالا آمدند؛ در حداقلی: ورود ✓، همهٔ مسیرهای پایه ۲۰۰ ✓، هر ۸ مسیر سیستم‌ها ریدایرکت دوستانهٔ «نصب نشده» با کد ماژول درست ✓، XHR با ۴۰۳ JSON ✓، toggle ماژول نصب‌نشده رد می‌شود ✓.
- **E2E**: `scripts/e2e-physical-p58.sh` — ۵۵ چک روی بستهٔ حداقلی (بدون DLL ماژول‌ها): گیت ۸ مسیر، واریانت صفحه، منو، نشان تنظیمات، ۱۶ مسیر پایه، ۷ بخش چند-ماژولی هاست (پرتال من/ESS/گزارش/خروجی)، وب‌هوک غایب ۴۰۴، toggle رد، فایل‌های استاتیک — ALL OK.
- **بسته‌های آماده** (فولدر `download/`): `HR-Platform-2.5.0-customer-FULL.zip` (۱۴۱MB → ۵۹MB فشرده، هر ۵ ماژول) و `HR-Platform-2.5.0-customer-MINIMAL-base-only.zip` (فقط پایه‌ها — نمونهٔ «مشتری بدون ماژول»).
- **نسخه**: 2.5.0. ساخت بستهٔ دلخواه: `scripts/build-customer.sh parking,payroll 2.5.0 "نام تولیدکننده"`.
