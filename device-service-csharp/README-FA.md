# HrDeviceGateway — سرویس ویندوزی مدیریت دستگاه‌های تردد (C# / ASP.NET Core 8)

سرویس بومی ویندوز برای مدیریت کامل دستگاه‌های حضور و غیاب، نوشته‌شده با **C# و ASP.NET Core 8**.
این سرویس، حلقه اتصال بین سامانه مرکزی (ASP.NET Core 8 MVC + SQL Server/SQLite) و دستگاه‌های تردد (ZKTeco و سازگار) است.

> **تفاوت با نسخه Node (`device-service/`):** این نسخه با .NET 8 کامپایل می‌شود، به‌صورت بومی به‌عنوان Windows Service اجرا می‌شود (بدون نیاز به Node.js)، و پروتکل TCP آن مطابق **مرجع استاندارد zkemsdk.c / pyzk** پیاده‌سازی شده است (ثابت‌های صحیح: `CMD_CONNECT=1000`، `CMD_UNLOCK=31`، `CMD_DELETE_USER=18` و…).

## ۱) معماری

```
┌──────────────────────────┐          REST/Bearer           ┌─────────────────────────┐
│   سامانه مرکزی (وب)      │ ◄────────────────────────────► │    HrDeviceGateway      │
│   ASP.NET Core MVC   │   /api/devices/webhook         │   ASP.NET Core 8        │
│   پورت 3000              │   /api/devices  /api/auth      │                         │
└──────────────────────────┘                                │  ┌───────────────────┐  │
                                                            │  │ Kestrel :8081     │  │
                    ┌───────────────────────────────────┐   │  │ پل ADMS/PUSH      │  │
                    │  دستگاه‌های ADMS (ZKTeco PUSH)    │──►│  └───────────────────┘  │
                    │  http://SERVER_IP:8081/iclock/... │   │  ┌───────────────────┐  │
                    └───────────────────────────────────┘   │  │ DeviceWorker      │  │
                                                            │  │ poller های TCP    │  │
                    ┌───────────────────────────────────┐   │  └───────────────────┘  │
                    │  دستگاه‌های مستقیم (پورت 4370)    │◄─►│  ZkTcpClient (باینری)   │
                    └───────────────────────────────────┘   └─────────────────────────┘
```

**دو حالت اتصال دستگاه:**
1. **ADMS (PUSH)** — دستگاه خودش به سرویس Push می‌کند (رایج در ZKTeco): آدرس دستگاه را روی `http://SERVER_IP:8081/iclock/cdata` تنظیم کنید. دستورات صف‌شده در پاسخ handshake تحویل می‌شوند (الگوی `C:{id}:…`) و رکوردهای تردد (ATTLOG) و کاربران (USERINFO) در POST دریافت می‌شوند.
2. **TCP مستقیم** — سرویس به پورت 4370 دستگاه متصل می‌شود و همه‌کار را خودش انجام می‌دهد: خواندن رکوردها، کاربران، اجرای دستورات، همگام‌سازی ساعت.

## ۲) قابلیت‌ها

| قابلیت | ADMS | TCP |
|---|:-:|:-:|
| دریافت رکورد تردد (ATTLOG / backfill از حافظه) | ✓ | ✓ |
| دریافت فهرست کاربران دستگاه | ✓ | ✓ |
| ثبت/به‌روزرسانی کاربر روی دستگاه (push_user — نام، کارت، سطح دسترسی) | ✓ | ✓ |
| حذف کاربر (با کد پرسنلی — حل خودکار uid) | ✓ | ✓ |
| بازکردن درب (unlock) | ✓ | ✓ |
| همگام‌سازی ساعت دستگاه با سرور | ✓ | ✓ |
| ری‌استارت دستگاه | ✓ | ✓ |
| نوسازی داده‌های داخلی (refresh_data) | ✓ | ✓ |
| پاک‌سازی رکوردها / کل داده‌ها | ✓ | ✓ |
| خواندن نسخه فریمور، شماره سریال، ظرفیت کاربر/رکورد | — | ✓ |
| تشخیص خودکار دستگاه آفلاین + اعلان به سرور | ✓ | ✓ |
| اجرای صف دستورات سرور + ACK کامل (delivered → acked) | ✓ | ✓ |

دستگاه TCP همچنین پس از هر poll، وضعیت (آنلاین، فریمور، شمارش کاربران) را به سرور گزارش می‌کند و رکوردهای تردد از حافظه دستگاه خوانده و با محاسبات شروع/خروج/دیرکرد سامانه ادغام می‌شوند.

## ۳) ساخت و انتشار

پیش‌نیاز: [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0) روی سیستم ساخت (ساخت روی ویندوز/لینوکس هر دو ممکن است).

```
device-service-csharp\
├── publish.bat                    ← انتشار برای ویندوز x64 (خودکفا، بدون نیاز به نصب runtime)
├── install-service.bat            ← نصب به‌عنوان Windows Service (Administrator)
├── uninstall-service.bat          ← حذف سرویس
├── HrDeviceGateway\               ← سورس پروژه
└── scripts\fake-tcp-device.mjs    ← شبیه‌ساز دستگاه برای تست
```

روی ویندوز: اجرای `publish.bat` → خروجی در پوشه `publish\` ساخته می‌شود (self-contained، نیازی به نصب .NET روی سرور هدف نیست).

## ۴) پیکربندی — کانفیگ پویا از پنل ادمین (از فاز ۲۱)

**تنظیمات اصلی و فهرست دستگاه‌ها از پنل ادمین خوانده می‌شود:**

> سامانه ← گروه «دستگاه‌ها» ← **«تنظیمات گیت‌وی»** (`/Gateway`)

در این پنل (بدون ویرایش فایل و بدون ری‌استارت سرویس):
- فعال/غیرفعال‌کردن پایش (توقف/ادامه Pollerها به‌صورت زنده)
- فاصله دریافت کانفیگ، فاصله پایش دستگاه‌ها، تایم‌اوت TCP، سطح لاگ
- پورت پل ADMS (تغییر پورت نیازمند ری‌استارت سرویس است — سرویس هشدار می‌دهد)
- پورت پیش‌فرض و CommKey پیش‌فرض دستگاه‌های TCP
- فهرست دستگاه‌های تحت مدیریت با badge نحوه اتصال (ADMS / TCP)

**فقط این موارد در `publish\appsettings.json` معنی دارند (نقش bootstrap):**

```json
{
  "Gateway": {
    "ApiBase": "http://APP_SERVER:3000",   // آدرس سامانه مرکزی
    "Username": "svc_bridge",              // کاربر پل سرویس (دسترسی devices.poll)
    "Password": "Bridge@1234",
    "ListenPort": 8081,                    // پورت اولیه پل ADMS (بعداً از پنل قابل تغییر)
    "Devices": []                          // fallback تا اولین دریافت موفق کانفیگ از سرور
  }
}
```

اگر سرور در دسترس نباشد، سرویس تا برقراری ارتباط با مقادیر bootstrap کار می‌کند و در لاگ هشدار می‌دهد. هر تغییر در پنل، `ConfigVersion` را بالا می‌برد؛ سرویس در چرخه بعدی (پیش‌فرض هر ۳۰ ثانیه) آن را اعمال و در لاگ ثبت می‌کند: «کانفیگ پویا اعمال شد (نسخه N)».

## ۵) نصب به‌عنوان Windows Service

1. `publish.bat` را اجرا کنید (خروجی self-contained — نیازی به نصب .NET روی سرور هدف نیست).
2. `publish\appsettings.json` را بررسی کنید — فقط `ApiBase` و حساب پل (`svc_bridge`) مهم است.
3. `install-service.bat` را **با دسترسی Administrator** اجرا کنید — این اسکریپت:
   - سرویس را با بازیابی خودکار (restart on failure) ثبت می‌کند؛
   - منبع Event Viewer («HrDeviceGateway») را ثبت می‌کند تا لاگ‌ها با منبع اختصاصی دیده شوند؛
   - سرویس را شروع می‌کند.

```bat
:: معادل دستی:
sc create HrDeviceGateway binPath= "C:\path\to\publish\HrDeviceGateway.exe" start= auto
sc failure HrDeviceGateway reset= 86400 actions= restart/5000/restart/10000/restart/60000
sc start HrDeviceGateway
```

- لاگ سرویس در **Event Viewer → Windows Logs → Application** (منبع: `HrDeviceGateway`).
- سلامت سرویس: `http://localhost:8081/health` — وضعیت runtime شامل enabled/configVersion/pollers/restartRequired.
- برای اشکال‌زدایی، exe را مستقیم از پوشه publish در حالت کنسول اجرا کنید (خروجی زنده در ترمینال).
- فایروال: پورت **8081** ورودی (برای دستگاه‌های ADMS) و اتصال خروجی به پورت **4370** دستگاه‌ها و پورت سامانه (3000) باز باشد.

## ۶) تنظیم دستگاه‌ها

### دستگاه‌های ADMS (ZKTeco با PUSH SDK)
در منوی دستگاه: `COMM → Cloud Server Settings`:
- Server Address = IP سرور ویندوزی
- Server Port = `8081`
-_Enable Domain Name = خاموش، Server URL = `/iclock/cdata`
پس از ذخیره، دستگاه هر چند ثانیه handshake می‌زند و در سامانه «آنلاین» می‌شود.

### دستگاه‌های مستقیم (TCP)
در پنل ادمین، هنگام تعریف/ویرایش دستگاه فیلدهای اتصال را پر کنید:
- **نحوه اتصال (Transport)** = `tcp`
- **IP دستگاه** و **پورت** (پیش‌فرض از کاتالوگ برند — معمولاً 4370)
- **CommKey** اگر روی دستگاه تنظیم شده

گیت‌وی در چرخه بعدی (حداکثر چند ثانیه) دستگاه را بدون ری‌استارت شروع می‌کند. کارت شبکه دستگاه باید از سرور قابل دسترس باشد.

## ۷) تست E2E (شبیه‌ساز)

```bash
# ترمینال 1 — شبیه‌ساز دستگاه TCP استاندارد
node scripts/fake-tcp-device.mjs 4370 ZK-U2000-0142

# ترمینال 2 — گیت‌وی (حالت کنسول)
cd HrDeviceGateway && dotnet run

# ترمینال 3 — شبیه‌ساز دستگاه ADMS
cd ../device-service && node scripts/fake-device.mjs ZK-FD7-0311 http://localhost:8081
```

سپس از سامانه (مدیریت دستگاه‌ها) دستور «باز کردن درب» یا «انتقال کاربر» صادر کنید و اجرای آن را در لاگ شبیه‌ساز و تب «لاگ دستورات» سامانه ببینید.

**نتیجه تست انجام‌شده در محیط توسعه:** اتصال/احراز TCP، خواندن بافر کاربران و رکوردها، ثبت تردد در سرور (با محاسبه دیرکرد)، اجرای unlock و push_user با ACK کامل، تحویل دستور ADMS و ACK دستگاه — همه با موفقیت تأیید شد.

## ۸) نکات فنی پروتکل

- قالب فریم TCP: `[50 50 82 7d][len:4 LE][cmd:2][chk:2][sid:2][rid:2][data]`
- چک‌سام با مدول **65535** (نه 65536) و مکمل یک — مطابق zkemsdk.c
- خواندن داده حجیم (کاربران/رکوردها): `PREPARE_BUFFER (1503) → PREPARE_DATA → READ_BUFFER (1504) → FREE_DATA`
- ساختار کاربر 72 بایتی: `uid@0, privilege@2, password@3, name@11, card@35, group@40, userId@48`
- ساختار رکورد تردد 16 بایتی: `userId@0, time@4, status@8, punch@9, workcode@12`
- کدگذاری زمان: `((y%100)*12*31 + (m-1)*31 + d-1)*86400 + h*3600 + mi*60 + s`
- نام کاربران با UTF-8 ارسال می‌شود و در صورت نیاز به Windows-1256 بازمی‌گردد (پشتیبانی فارسی).

## دوربین‌های پلاک‌خوان (ANPR) — از نسخه ۲.۱

گیت‌وی علاوه بر دستگاه‌های تردد ZK، **دوربین‌های پلاک‌خوان پارکینگ** را هم پل می‌کند:

```
┌──────────────────────────┐   Bearer svc_bridge    ┌─────────────────────────┐
│   سامانه مرکزی (وب)      │ ◄────────────────────► │    HrDeviceGateway 2.1  │
│   api/anpr/webhook       │   ضربان + پلاک + ack    │                         │
└──────────────────────────┘                         │  ┌───────────────────┐  │
                    ┌───────────────────────────────┐│  │ AnprBridge        │  │
                    │ دوربین پلاک‌خوان (HIK/Dahua…)  │→│  │ POST /anpr/plate  │  │
                    │ http://SERVER_IP:8081/anpr/…  ││  └───────────────────┘  │
                    └───────────────────────────────┘│  DeviceWorker: حلقه     │
                                                     │  ضربان + اجرای راهبند   │
                                                     └─────────────────────────┘
```

### ۱) نحوه کارکرد

- **فهرست دوربین‌ها** از پنل ادمین به‌صورت پویا می‌آید (`api/gateway/config → cameras`) — دوربینِ فعال‌شده در تب «دوربین‌های پلاک‌خوان» پارکینگ، تا ۳۰ ثانیه بعد در گیت‌وی حلقه می‌گیرد.
- **ضربان**: حلقه هر دوربین به‌فاصله `HeartbeatSec` ثانیه `GET api/anpr/webhook?SN=…` می‌زند؛ سرور `LastSeenAt` را تازه می‌کند → دوربین در پنل «آنلاین» است، بدون نیاز به خط مستقیم بین دوربین و گیت‌وی.
- **پلاک**: دوربین (یا نرم‌افزار واسط سازنده) خوانش را به `POST http://SERVER_IP:8081/anpr/plate?SN=…` می‌زند؛ گیت‌وی نرمال می‌کند و به موتور مجوز پارکینگ می‌رساند. پاسخ سرور (نتیجه، باز/بسته بودن راهبند، مالک) عیناً برمی‌گردد.
- **راهبند**: دستور «🔓 راهبند» پنل در ضربان تحویل و به قالب HTTP خود دوربین رله می‌شود — پیکربندی در `appsettings.json`:

```json
"Gateway": {
  "Anpr": {
    "Enabled": true,
    "HeartbeatSec": 30,
    "Cameras": [
      {
        "Serial": "ANPR-PG-IN1-1024",
        "Ip": "10.10.4.21",
        "OpenUrl": "http://{ip}/ISAPI/System/IO/outputs/1/trigger",
        "RestartUrl": "http://{ip}/ISAPI/System/reboot",
        "HttpUser": "admin",
        "HttpPass": "…"
      }
    ]
  }
}
```

`Serial` باید دقیقاً همان سریال ثبت‌شده در پنل باشد؛ `{ip}` با IP دوربین جایگزین می‌شود؛ `CloseUrl` اختیاری است؛ `HttpUser/HttpPass` برای Basic Auth خود دوربین است. **اگر قالب تنظیم نشده باشد، دستور با پیام راهنمای فارسی «failed» می‌شود** (نتیجه در تب دوربین‌ها دیده می‌شود).

### ۲) قرارداد پل پلاک — برای تنظیم دوربین/یکپارچه‌ساز

| مسیر | متد | بدنه پذیرفته‌شده |
|---|---|---|
| `/anpr/plate?SN=…` یا `/anpr/{sn}/plate` | POST | JSON تکی `{"plate":"27ب۳۴۵ایران۳۶","direction":"in","confidence":93}` · JSON دسته‌ای `{"reads":[…]}` · form `plate=…&direction=…` · متن خام (کل body = پلاک) · query `?plate=…` |
| `/anpr/ping?SN=…` یا `/anpr/{sn}/ping` | GET | ضربان + شمارش دستورات در انتظار |

- نام فیلدهای رایج سازنده‌ها پذیرفته می‌شود: `plate / plateNo / plateNumber / plate_number / carNumber`، جهت: `direction / dir / lane`، اطمینان: `confidence / score / similarity`.
- جهت به فارسی نرمال می‌شود: `in/enter/ورودی → «ورود»` و `out/exit/خروجی → «خروج»`.
- پلاک را **کامل با کد ایران** بفرستید (`27ی915 ایران 36`) — موتور سرور با نرمال‌سازی داخلی تطبیق می‌دهد؛ پلاک ناقص «فاقد مجوز» حساب می‌شود.
- پاسخ: `{"ok":true,"okCount":1,"failed":0,"result":"مجاز","barrier":"open","owner":"جواد صادقی",…}` — در خطا، کد و پیام سرور عیناً پاس داده می‌شود (مثلاً 404 دوربین ناشناس).
